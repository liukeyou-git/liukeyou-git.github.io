## 前言

亚马逊产品上架并非简单的"填表提交"，其底层是一套基于 Flat File（扁平文件）模板的批量数据交换架构，涉及严格的 Schema 校验、状态流转控制与处理报告反馈机制。而 A+ 内容创建则是一套模块化的富媒体渲染系统，需要遵循像素级规范、响应式布局规则与多层审核机制。本文从技术视角拆解这两条核心流程的实现细节。

## 一、产品上架流程：技术架构与系统交互

### 1.1 整体技术架构

亚马逊产品上架基于 **Flat File 批量上传机制**，其技术架构可抽象为三层：

- **模板层**：Excel 工作簿（.xlsx），由 Seller Central 按类目动态生成，包含 Schema 定义、枚举值约束与示例数据
- **传输层**：通过 Seller Central 的 `Add Products via Upload` 接口提交，文件转换为 .txt/.csv 后经 MWS（Marketplace Web Service）管道处理
- **处理层**：亚马逊后端的 Feed Processor 逐行解析、校验、入库，并生成 Processing Report 反馈结果

整个交互链路为：`Catalog → Add Products via Upload → Download Template → 填充数据 → Upload → Feed Processing → Processing Report`

### 1.2 模板结构：七表架构

下载的 Flat File 是一个多工作表的 Excel 文件，每个 Sheet 承担不同职责：

| Sheet 名称 | 职责 | 技术作用 |
|-----------|------|---------|
| **Instructions** | 使用说明 | 类目规则、字节限制、枚举值说明 |
| **Data Definitions** | 数据字典 | 每列的数据类型、必填级别（Required/Preferred/Optional）、有效值范围 |
| **Valid Values** | 枚举值表 | 下拉字段的合法取值（如 Item Type、Condition），自由文本会被拒绝 |
| **Template** | 数据录入表 | 唯一允许编辑的 Sheet，表头固定不可重排 |
| **Example** | 示例数据 | 展示正确填写的样本行 |

关键约束：**只有 Template Sheet 可写入数据**，其余 Sheet 仅供引用。表头顺序、列名不可修改，否则 Schema 校验阶段整文件被拒。

### 1.3 四个核心列：决定 Feed 行为

Template 表虽有数十至数百列，但有四列决定了整个 Feed 的执行语义：

- **`item_sku`**：卖家内部标识符，每行必填。这是亚马逊定位目录中已有 Listing 的主键，决定是创建还是更新
- **`external_product_id` + `external_product_id_type`**：GTIN/EAN/UPC/ASIN 及类型码。创建新 Offer 或关联已有 ASIN 时必填；纯内容更新可省略
- **`update_delete`**：行意图控制符，**最危险的字段**
  - `Update`（默认）：创建缺失 Listing 并覆盖行内所有字段，**空单元格会被视为"清空该字段"**
  - `PartialUpdate`：仅更新填写的单元格，空单元格保持线上值不变
  - `Delete`：移除该 ASIN 的 Offer
- **`feed_product_type`**：类目叶节点标识符，创建时必填，错误值会导致整行被拒

`Update` 是默认值也是最大风险点——对已存在 SKU 使用 `Update` 且留空字段，会批量清空线上数据。生产环境中，**内容更新应始终显式切换为 `PartialUpdate`**。

### 1.4 数据验证机制

亚马逊对 Flat File 实施多层校验：

- **Schema 校验（前置）**：检查列结构、数据类型、必填项。此阶段失败会拒绝整个 Feed
- **枚举值校验**：`Valid Values` 表定义的字段，自由文本直接拒绝该行
- **业务规则校验**：如价格格式（USD `29.99` 而非 `29,99`）、尺寸单位（英寸/磅）、日期格式（MM/DD/YYYY）、变体关系合法性
- **唯一性校验**：SKU 全局唯一，Product ID 在类目内唯一

校验失败的信息通过 Processing Report 反馈，报告按行记录错误代码、出错列名与具体原因，支持精准定位修复。

### 1.5 状态流转模型

单个 SKU 在上传后的状态流转：

```
Submitted → Processing → [Validated] → Active
                         ↓
                      [Rejected] → 修正后重新提交
                         ↓
                      [Warning] → 部分字段未生效，Listing 仍上线
```

- **Submitted**：文件已上传，等待处理队列调度
- **Processing**：Feed Processor 逐行解析校验
- **Validated → Active**：通过校验，Listing 上线可搜索
- **Rejected**：严重错误，整行拒绝，需根据 Processing Report 修正后重传
- **Warning**：非致命问题（如图片 URL 暂时不可达），Listing 上线但需后续修复

### 1.6 处理报告解析

上传完成后在 `Monitor Upload Status` 下载 Processing Report，该报告是一个 .txt 文件，逐行记录：

- `Batch ID`：本次上传批次号
- `Record Number`：出错的行号
- `error-code`：错误代码（如 `5000` 表示字段缺失、`8541` 表示 Product ID 不匹配）
- `field-name`：出错的列名
- `message`：具体错误描述

通过错误代码可精准定位问题。常见错误：`8541`（GTIN 不匹配已有 ASIN）、`5000`（必填字段缺失）、`8801`（枚举值非法）、`13013`（变体关系冲突）。

## 二、A+ 内容创建流程：模块化富媒体系统

### 2.1 三种内容类型

A+ 内容是品牌注册卖家专属的富媒体描述层，运行在 A+ Content Manager 中，提供三种类型：

| 类型 | 渲染位置 | 模块上限 | 可选模块数 | 核心能力 |
|------|---------|---------|-----------|---------|
| **Basic A+** | 产品描述区段 | 5 | 14 | 图片+文本、对比图、标准模块 |
| **Premium A+** | 产品描述区段（增强） | 7（2026 扩展至 15） | 19 | 交互热点、视频、轮播、增强对比表、Q&A |
| **Brand Story** | "来自品牌"区段 | 1（含 19 张卡片） | — | 全屏背景、卡片轮播、品牌商店链接 |

2026 年起，Premium A+ 已向所有品牌注册卖家免费开放，无需额外销售门槛。

### 2.2 模板结构：模块化架构

A+ 内容采用**模块化组合架构**，每个 A+ 页面由若干 Module 按顺序堆叠组成。核心模块类型：

- **Full Image**：全宽图片模块，桌面 970×300px（Basic）/ 1464×600px（Premium）
- **Images & Text**：图文混排模块，支持单图、双图、四图布局
- **Comparison Chart**：对比表模块，支持自有产品对比或与"典型市场替代品"对比
- **Text**：纯文本模块，字符上限高于其他模块，适合详细说明
- **Hotspots**（Premium）：交互热点，鼠标悬浮触发产品细节
- **Video**（Premium）：视频模块，支持多支视频
- **Carousel**（Premium）：轮播模块
- **Q&A**（Premium）：问答模块
- **Technical Specifications**：技术规格表，**少数可被搜索引擎索引的模块**（alt text 会被抓取）

模块排列需遵循叙事弧线：品牌故事 → 核心功能 → 对比表 → 使用场景 → 信任收尾。错误顺序（如对比表前置）无法靠视觉弥补。

### 2.3 富媒体处理规范

A+ 所有图片遵循统一的底层规范：

- **格式**：JPG、BMP、PNG（不支持 GIF/WebP/动图）
- **文件大小**：单张 ≤ 2MB
- **分辨率**：≥ 72 dpi
- **色彩空间**：RGB（不支持 CMYK）
- **源文件**：建议 300 DPI 起步，即使 Web 端会压缩

各模块的精确尺寸规格：

| 模块 | 桌面尺寸 | 移动尺寸 | 字符限制 |
|------|---------|---------|---------|
| Premium Full Image | 1464×600 | 600×450 | Headline 80 / Body 300 |
| Premium Background+Text | 1464×600 | 600×450 | Sub 40 / Head 60 / Body 300 |
| Premium 4 Images & Text | 300×225（每图） | 复用桌面资源 | Sub 80 / Head 30 / Body 150 |
| Standard Hero | 970×300 | — | — |
| Comparison Chart 图标 | 150×150（PNG 透明） | — | — |
| Brand Story 背景 | 1464×625 | — | — |

像素级合规是硬性要求：超出尺寸会被直接拒绝，或被系统裁剪导致布局错乱。

### 2.4 响应式设计机制

A+ 内容需同时适配桌面端与移动端，其响应式策略：

- **双图源机制**：部分模块支持桌面图与移动图分别上传（如 Full Image 桌面 1464×600、移动 600×450）
- **单图复用降级**：未提供移动图时，系统自动裁剪桌面图适配，但可能丢失关键信息
- **布局重排**：桌面端四列网格在移动端自动堆叠为单列；对比表桌面为表格、移动为卡片堆叠
- **滚动行为**：移动端买家平均滚动约 2400px 后跳出，约等于 9 个标准模块高度——超过 10 个模块收益递减

设计时需保证移动端首屏（前 2-3 个模块）承载核心信息，避免关键卖点被折叠在下方。

### 2.5 内容审核机制

A+ 内容提交后经过**自动审核 + 人工审核**双层校验。自动审核基于规则引擎拦截明显违规，人工审核处理边界情况。

**九类高频拒绝原因**：

1. 引用客户评价或星级评分
2. 包含价格、折扣百分比、"限时"等促销语言
3. 文本或图片中出现竞品品牌名
4. 无佐证的声明（如"#1 评分"、"临床验证"）且无可视化引用来源
5. 联系方式：邮箱、电话、amazon.com 以外的 URL
6. 版权角色（迪士尼、体育联盟等）即使有授权但无可见 License
7. 文本覆盖图片面积超过 30%（自动拒绝）
8. 低分辨率图片（低于 72 dpi）
9. 文案与对应图片不相关

审核未通过会返回具体原因，修正后可重新提交。审核周期通常为数小时至数天。

### 2.6 AI 生成内容合规标记

当 A+ 内容包含拟真 AI 生成人物时，必须添加合规元数据：

- **图片标记**：在 A+ Content Manager 的创意资产库上传图片时，勾选"AI 生成人物"选项，系统自动注入元数据
- **视频标记**：使用 IPTC 兼容的元数据编辑器，在视频文件的 `dc:subject`（XMP）字段添加关键字 `contains-synthetic-performer`

**无需标记的情况**：仅含真实人物（即使经 AI 辅助修饰）、仅含影视/游戏角色、无人物、非拟真外观人物。

批量处理场景下，可通过脚本化工具批量注入 `contains-synthetic-performer` 标签，显著提升 A+ 页面制作效率。

### 2.7 A/B 测试机制

A+ 内容支持通过 `Manage Your Experiments` 进行 A/B 测试：

- 创建内容变体（Version A / Version B）
- 系统自动分流流量，收集转化数据
- 达到统计显著性后自动推广获胜版本

建议优先对 Hero 模块（首屏全宽图）和对比表模块进行测试，这两类模块对转化率影响最大。

## 三、问题解决与工程实践

### 3.1 图片资源缺失的处理策略

上架过程中常遇图片资源不全的情况，处理逻辑：

- **主 SKU 查询**：优先检查主 SKU 是否包含所需图片资源，子 SKU 可复用父级资产
- **图片前移策略**：若资源仍不足，将后续图片前移填补空位，确保主图位（main_image_url）非空
- **单色款判定**：确认产品为单色单款时，现有图片即可满足基础上架需求，无需强行补充多角度图

### 3.2 版本管理与回滚

Flat File 应建立版本管理机制：

- 每次上传前保存原始模板为 master 副本
- 每次上传生成带日期命名的副本（如 `Womenswear_Template_2026-08-02`）
- 上传后保存 Processing Report 与 Batch ID
- 出现 Listing 被抑制或需回滚时，可快速恢复至先前版本

### 3.3 批量操作效率优化

- 始终下载最新类目模板（亚马逊定期更新字段与合规要求），避免使用过期模板导致 Schema 校验失败
- 内容更新场景显式设置 `update_delete = PartialUpdate`，防止空单元格清空线上数据
- 善用 Data Definitions Sheet 作为校验依据，提交前逐项核对必填字段与枚举值
- 对 AI 图片批量注入合规标记，脚本化处理优于手工逐张勾选

## 四、技术要点总结

### 产品上架流程

| 维度 | 关键技术点 |
|------|-----------|
| 架构 | 三层架构（模板层/传输层/处理层） |
| 模板 | 七表结构，仅 Template Sheet 可写 |
| 核心字段 | item_sku / external_product_id / update_delete / feed_product_type |
| 状态控制 | Update（覆盖）/ PartialUpdate（部分）/ Delete |
| 验证 | Schema 校验 + 枚举校验 + 业务规则 + 唯一性 |
| 反馈 | Processing Report 逐行错误码定位 |

### A+ 内容创建流程

| 维度 | 关键技术点 |
|------|-----------|
| 类型 | Basic / Premium / Brand Story |
| 架构 | 模块化堆叠，遵循叙事弧线 |
| 富媒体 | JPG/PNG ≤2MB，RGB，72dpi+ |
| 响应式 | 双图源机制 + 布局重排 + 移动首屏优先 |
| 审核 | 自动规则引擎 + 人工审核，九类拒绝原因 |
| AI 合规 | contains-synthetic-performer 元数据注入 |
| 优化 | Manage Your Experiments A/B 测试 |

## 五、后续优化方向

- **Listing 上线后监控**：持续跟踪搜索词报告、转化率、广告 ACOS，反向优化内容
- **A+ 内容迭代**：基于 A/B 测试数据持续优化模块组合与视觉呈现
- **流程标准化**：将上架与 A+ 创建流程沉淀为操作手册，降低人员依赖
- **自动化探索**：通过 MWS API / SP-API 实现上架流程的自动化集成，减少手工模板操作
